# Trade Terminal: implementation plan to production

Drafted 2026-10-25. Supersedes the 2026-10-01 production readiness plan and the older *Terminal Build Order* artifact. It keeps their engine-first approach and their gates, and adds three things: the natural-language agent designed in detail, the session-scoped data cache you asked for, and the issues found in a fresh-clone audit of this repo on 2026-10-25.

Item IDs (P0.1, P2.3, ...) are stable, so you can say "start P1" or "drop P5.2".

---

## 1. What we are building

A trader installs Trade Terminal on their own machine and can, without writing JSON or code:

1. **Describe** a strategy in plain English (or Hinglish, or trader shorthand like "ORB with CPR filter, SL at day low").
2. **Confirm** it: the app answers at most two clarifying questions, then shows an exact read-back of what it understood, which the trader approves or edits.
3. **Test** it: a backtest runs with no manual download step. The data the run needs is fetched and cached for the session.
4. **Understand** it: a report, plus a plain-English explanation built only from the computed numbers.
5. **Refine** it in conversation ("tighten the stop to 0.5%", "only trade after 9:30"). Every change becomes a new version.
6. **Apply** it: one click starts paper trading. Live trading comes last, behind its own gates (Phase 7).
7. **Decide what happens to the data.** Market data downloaded while the app is open is cached for that whole app session, across every strategy. When the trader quits, it's discarded or kept on the machine; the trader chooses, and can tick *Remember my preference*.
8. **Come back later.** Conversations, strategies and results are saved permanently, so the trader can reopen any past chat and its strategies, whatever happened to the market data.

Everything else in the product (templates, the visual builder, the strategy library, alerts, the data manager, later the screener and research agent) serves that loop.

### Scope: local app first, hosted version later (decided 2026-10-28)

Phases 0 to 7 build the local app each trader installs. A hosted, multi-user version (accounts, subscriptions, server-side execution, comparable to platforms such as Rapfin Autopilot) comes afterwards as Phase 8. To keep that path open without paying for it now, Phase 1 onward follows four rules:

1. **Every app-state row has an owner.** Tables carry a `user_id` column that is always `"local"` in the local app, so the hosted version is a data migration, not a schema redesign.
2. **No per-user state in module globals.** Paths, settings and caches are reached through a context object that today wraps the single local user.
3. **One auth seam in the API.** Every router takes the current user from a single dependency, which returns the local user now and a logged-in user later.
4. **Storage and jobs behind interfaces.** The data service, the job runner and the app database are used through small interfaces, so hosted deployments can swap in server-grade backends (Postgres, a task queue, object storage) without touching callers.

### Product principles

- **The engine stays the source of truth.** The language model writes a strategy document; it never computes P&L, never invents metrics, and never sits in the order path.
- **Humans approve, code checks.** Every LLM output passes strict validation. The read-back the trader approves is generated by code from the actual spec, not written by the model.
- **The user owns their data and their edge.** The app is local-first: strategies, results and (if the user chooses) market data stay on their machine. The only outbound calls are to the broker and the LLM provider, and both are disclosed.
- **Works without an LLM, and without a broker.** The visual builder and templates keep working with no API key. Simulated data and CSV import let someone try the product before connecting Upstox.

### What "production-ready" means here

| Milestone | Ends after | You can say |
|---|---|---|

## 4. Session-scoped data cache, retention and history

Download market data only when it's needed, keep it cached while the trader is using the app, and let them decide when they quit whether it's discarded or kept. Conversations and strategies are always saved.

### 4.1 What a "session" is

An **app session** runs from the moment the trader opens Trade Terminal until they quit it. Everything downloaded in that time goes into one shared session cache, whichever strategy or conversation needed it. If a trader works on three strategies that need NIFTY 5m, BANKNIFTY 1m and RELIANCE daily, all three datasets stay cached until they quit, and every re-run and refinement reads from the cache with no new downloads.

**What "quitting the app" means.** Trade Terminal is a local server plus a UI, so closing a browser tab isn't the same as quitting. The session ends when either of these happens:

- **The trader quits explicitly:** a *Quit* button in the UI now, and closing the window once the desktop wrapper ships (P4.4). This is the normal path, and it shows the Keep/Discard dialog.
- **The trader has gone offline:** no UI tab has been connected for 30 minutes and no paper session is running (decided 2026-10-25). This matches "as long as the user is online". Their remembered preference is applied; with no remembered preference, the data is held and they're asked at next launch.

If a paper session is running, quitting warns that it will stop the session (P0.4).

### 4.2 The quit dialog and preferences

At quit, a dialog lists what was downloaded this session, for example "NIFTY 5m (Jan–Oct 2026), BANKNIFTY 1m (Jun–Oct 2026): 61 MB", with two buttons, **Keep on this machine** and **Discard**, and a **Remember my preference** checkbox.

| Preference | What happens at quit |
|---|---|
| **Ask every time** (default) | The dialog above |
| **Always keep** | Session data joins the local library and is reused next time; no dialog |
| **Always discard** | Session data is deleted; no dialog |

Ticking the checkbox saves the choice as *Always keep* or *Always discard*. The trader can change it any time in Settings. The Data Manager page shows the size of the kept library per instrument, lets the trader delete any of it, and offers an optional size cap (least-recently-used data is evicted first). A status-bar indicator shows the current session cache size.

### 4.3 How it works

Two physical stores:

```
data/store/                       kept library (permanent)
data/scratch/<app_session_id>/    this app session's cache (deleted or promoted at quit)
```

- `get_bars(instrument, timeframe, start, end)` reads the kept library first, then the current session's scratch, then downloads only the missing trading sessions into scratch. With *Always keep* set, it writes straight into the library and nothing needs promoting at quit.
- **Discard** is `rm -rf data/scratch/<app_session_id>`: simple, complete and easy to verify. That matters if "the data goes away" is a privacy promise.
- **Keep** promotes scratch into the library with the same atomic, locked merge as P0.2, with a progress bar, then deletes scratch. If promotion is interrupted, scratch is left intact and promotion resumes at next launch, so nothing is lost or half-written.
- **Unclean exits** (crash, power loss, laptop lid, `kill -9`) can't show a dialog. At next launch, any leftover scratch folder is handled by the remembered preference, or, with *Ask every time*, a prompt: "Data from your last session (61 MB) wasn't saved or discarded. Keep or discard?"
- **Long sessions:** a trader who leaves the app open for days keeps one growing cache. The size cap (if set) evicts least-recently-used session data during the session, and the status-bar indicator keeps the size visible.

### 4.4 Conversation history (always saved)

Conversations aren't market data, and they're kept permanently whatever the data preference:

- **What's saved:** every conversation's messages, the clarifying questions and answers, the assumptions, every strategy version it produced (linked by content hash), and every run started from it (linked by run ID).
- **History sidebar:** a list of past conversations with title, date, instrument and latest result, plus search. Opening one shows the full chat, the strategy versions and their results.
- **Continuing an old conversation:** the trader can reopen a past chat and keep refining. If its graph checkpoint still exists, it resumes exactly where it paused; if not, a new graph thread starts from the conversation's latest strategy version, with the old messages shown above.
- **Re-running when the data was discarded:** results stay viewable (metrics, trades and charts are stored with the run). A re-run downloads the data again and checks the fingerprint (§4.5).
- **Trader control:** rename, delete, or export a conversation (Markdown or JSON, with its strategy specs). Deleting a conversation never deletes strategies saved to the library.
- **Storage:** messages live in SQLite for display and search. LangGraph checkpoints are stored separately and are pruned after 15 days, so a conversation can be resumed exactly where it paused for 15 days; after that, continuing it starts a new graph thread from its latest strategy version. The readable history is kept forever (decided 2026-10-25).

### 4.5 Rules that apply in every mode

- **Download only base timeframes:** 1-minute (intraday) or daily. 3m, 5m, 15m and 1h are derived locally, bucketed from 09:15. A parity test checks that derived 5m equals Upstox's native 5m on stored data.
- **Fetch only what's missing,** merged into a few ranges. Past sessions are immutable once fetched; only the last few days are re-checked. Sessions with no data (holidays, pre-listing) are remembered so they aren't re-requested.
- **Before a run, show a data plan:** what will be downloaded, roughly how big, and an ETA under rate limits. Downloads run as a job with progress and cancel.
- **Results never depend on the data still existing.** Every run stores a data fingerprint (instrument, range, row count, content hash). Re-running a strategy whose data was discarded re-downloads it and checks the fingerprint. A mismatch (for example, Upstox revised a candle) is shown, not hidden.
- **Not subject to retention:** the instrument master (small reference data, needed for search), conversations, strategies, run results, and journals. Journals are the trade record and are needed for crash recovery. When session data is discarded, a journal's bar events can be stripped, keeping orders, fills and P&L.
- **Simulated data** follows the same rules; it's regenerable from its seed.

### 4.6 Open question that gates the Keep option

Do Upstox's API terms limit how long market data may be stored locally? This is desk research (P0.10) and decides whether *Keep* can ship as designed. If storage is restricted, discard-at-quit becomes the only behaviour, or kept data gets a time limit. The session cache works either way.

## 5. The natural-language agent

### 5.1 The flow

```
 user text ─► understand ─► clarify? ─► compile ─► lower ─► validate ─┐
                 │          (≤2 Qs,     (LLM →     (IR →    (schema + │
                 │          interrupt)   IR)       Strategy) registry │
                 │                         ▲                + semantic)
                 │                         └── errors, max 3 repairs ─┤
                 ▼                                                    ▼
          question / help ◄───────────────────────────────── read-back (code-generated,
          (answered in chat)                                 interrupt: approve / edit)
                                                                      │ approved
                                       explain ◄── backtest ◄── data plan
                                     (numbers from   (job)      (size, ETA)
                                      metrics only)
                                          │
                     refine (patch) ◄─────┤ "tighten the stop…"
                     → lower → validate → read-back (new version)
                                          │
                                          ▼
                              ready to apply → [Start paper] button (human click, plain API call)
```

### 5.2 Key design decisions

1. **An LLM-facing intermediate format (the "compile IR"), not the engine schema.** Claude's structured outputs guarantee valid JSON only for non-recursive schemas with `additionalProperties: false` everywhere. The IR is therefore:
   - condition nesting capped at two levels (a group of conditions or sub-groups of conditions), which covers essentially every trader-described strategy; deeper logic stays available in the visual builder;
   - indicator parameters as an explicit list of `{name, value}` pairs, validated against the indicator registry;
   - no inline indicators (every indicator is declared and named);
   - `assumptions` and `open_questions` fields that the model fills in.

   A deterministic, tested `lower()` function turns IR into the canonical `Strategy`. The engine schema stays free to evolve (schema v2 in P4.2) without retraining prompts, and round-trip tests (`Strategy → IR → Strategy` keeps the content hash identical for every template) keep the two in step.
2. **The read-back is code, not prose from the model.** A deterministic renderer turns the validated `Strategy` into plain English plus a compact table (entry, exit, legs, sizing, risk, session times, assumptions). The trader approves exactly what will run. The model may add a friendly one-line summary, but it's never the thing approved.
3. **Validation has three layers:** pydantic schema; registry checks (indicator exists, every param known and in range, which fixes finding 19); semantic preflight (timeframe available for the instrument, option legs valid for the underlying, session window inside market hours, lookback shorter than the data range). Errors go back to the model as structured feedback, with at most 3 repair loops; after that the trader sees the problem and can fix it in the builder.
4. **Clarify asks at most two blocking questions.** Everything else becomes a listed assumption the trader can change in the read-back. Questions use LangGraph `interrupt()`, so a paused conversation survives an app restart (SQLite checkpointer).
5. **Refine produces patches.** A follow-up message becomes a change to the current IR, re-lowered, re-validated and re-read-back. Each approved version is a new content hash in the library, with a parent link, so history and diffs come for free.
6. **Edits in the visual builder flow back.** If the trader edits the read-back in the builder, the graph receives the edited spec as the new current version and continues from there. Chat and builder never disagree.
7. **Explanations are grounded.** The explain step receives computed metrics and trades, not raw data. A grounding check verifies that every number in the explanation matches a computed value (within rounding); if not, the explanation is regenerated or dropped.
8. **The agent can't apply strategies.** The graph ends at "ready to apply". Starting paper is the trader's click on an ordinary API endpoint. The same rule carries over to live trading in Phase 7.

### 5.3 LangGraph: why, and how to keep it thin

LangGraph earns its place for three reasons: interrupts with durable checkpoints (approval pauses that survive restarts), streaming node events to the UI, and `Send` fan-out for the research agent in Phase 6. To keep it from spreading:

- graph nodes are thin wrappers around plain Python functions in `backend/agent/steps/`, which are unit-tested without LangGraph;
- the LLM is called through our own adapter (P2.1) using the provider SDK directly, so there is no LangChain model dependency;
- LangGraph and its SQLite checkpointer are pinned in the lockfile.

### 5.4 LLM provider and cost

- **Default:** Anthropic Claude through the official `anthropic` SDK. Start with `claude-opus-5-5` (US$4 / US$20 per million input/output tokens as of October 2026) for compile and repair. The Phase 4 eval measures whether `claude-sonnet-5-5` (US$2 / US$10) or `claude-haiku-5-5` (US$0.10 / US$0.50) hold accuracy for some steps (understand and clarify are good candidates), and routing changes only on eval evidence.
- **Adapter interface** from day one, with one implementation at M1. Ollama (local models, for privacy) is the second provider, added in Phase 4 if the eval shows a usable local model. OpenAI and Gemini are added only if beta users ask.
- **Implementation notes for current Claude models:** use structured outputs (`output_config.format`) for the IR, because forced `tool_choice` is rejected on Opus 5.5 and Sonnet 5.5. Check `stop_reason` (handle `refusal` and `max_tokens`) before reading output. Cache the system prompt and schema with prompt caching. Set `effort` explicitly (Opus 5.5 defaults to `medium`).
- **Rough cost per strategy compile:** about 6k input and 2 to 4k output tokens including a repair, so roughly US$0.05 to 0.15 on Opus 5.5 before caching. This is an estimate; P4.1 measures it.
- **Billing model for beta:** bring your own API key (stored in the OS keychain). A hosted key would make the app a paid service with its own costs and compliance questions; revisit after M2.
- **Caps:** per-compile limits on tokens, steps and wall-clock; a visible cost counter per conversation; an optional monthly budget in settings.

### 5.5 Safety, privacy and provenance

- **Untrusted input:** pasted transcripts, posts and messages are data. The model has no tools with side effects, and its only output is an IR that code validates, so injected instructions can at worst produce a strategy the trader then sees in the read-back.
- **Privacy disclosure:** the Studio says plainly that strategy descriptions are sent to the chosen LLM provider. A local-model option (Ollama) is the privacy path.
- **Provenance:** every strategy version records its source (`llm`, `builder`, `template`, `import`), plus the model ID, prompt version and conversation ID when it came from the LLM. A result can always be traced to the exact spec and to how that spec was produced.
- **LLM call log:** model, prompt version, tokens, cost, latency, request ID and a redacted prompt/response, kept locally for debugging and for building the eval set.

### Phase 1: Platform foundation (3 to 4 weeks)

- **P1.1 App database.** SQLite in WAL mode with versioned migrations. Tables: `strategies`, `strategy_versions` (content hash, parent hash, spec JSON, provenance), `app_sessions` (started, ended, how it ended, scratch size, outcome), `preferences` (retention preference, idle timeout), `conversations` and `messages` (permanent history, full-text search), `runs` (strategy hash, kind, params, data fingerprint, metrics, status), `jobs`, `llm_calls`, `data_coverage`, `cache_index`, plus LangGraph checkpoint tables. Coverage metadata moves from DuckDB to SQLite; DuckDB becomes an in-process, read-mostly analytics engine over Parquet, which removes the single-writer conflict.
- **P1.2 Job runner.** Background jobs for fetch, backtest and (later) sweeps and scans: job ID, progress, ETA, cancel, result pointer. Progress streams to the UI over SSE. Long work leaves the request threads (finding 6). The MCP server in Phase 5 reuses it.
- **P1.3 Data service.** `get_bars()` as the single entry point, per §4.4: base-timeframe downloads only, local derivation, gap-aware fetch, holiday memory, data plan with size and ETA, fingerprints. Parquet partitioned by instrument, base timeframe and month (sized for the option-contract volume P4.3 may bring). Migrate existing per-timeframe files.
- **P1.4 Session cache and retention.** The design in §4.1 to §4.3: one scratch cache per app session, shared by every conversation; the quit endpoint and the idle-offline rule (no UI connected for 30 minutes and no paper session); the three preferences (Ask every time, Always keep, Always discard); promotion with resume; the startup prompt for leftover scratch after an unclean exit; the in-session size cap; the journal compaction option. Tests: discard leaves no file behind; promotion is atomic and resumes after a simulated crash; a `kill -9` mid-session leads to the startup prompt; a re-run after discard reproduces the same fingerprint; two conversations in one session share cached data with zero duplicate downloads.
- **P1.5 Strategy library and run history.** CRUD with version history (content hash, parent, provenance), templates imported as read-only library entries, a run history per strategy, and a **trial counter** per strategy family (every backtest recorded, so deflated Sharpe is possible in Phase 6).
- **P1.6 API restructure.** Split the 724-line `main.py` into routers; a consistent error model; generate a typed TypeScript client from OpenAPI so the UI and API can't drift.

**Gate:** a backtest on a clean data dir fetches what it needs as a cancellable job with progress; quitting with *Discard* removes every downloaded file; *Keep* reuses data with zero network calls in the next app session; a second strategy on the same data in the same session makes no network calls; conversations survive restarts; existing parity, crash-recovery and lookahead tests stay green.

### Phase 2: Agent layer (4 to 5 weeks)

- **P2.1 LLM adapter.** A provider interface (structured compile, chat, streaming, token and cost accounting); a Claude implementation through the `anthropic` SDK; API keys in the OS keychain (`keyring`), never in `.env` or logs; per-compile caps; the `llm_calls` log; refusal and `max_tokens` handling.
- **P2.2 Compile IR and lowering.** The IR schema in §5.2 (non-recursive, closed objects); `lower()` and `raise_()` with round-trip tests over all templates; registry-backed param validation; a glossary of Indian-market terms for the prompt (CPR, ORB, ATM/OTM, straddle/strangle, SL/TSL, BTST, expiry-day conventions).
- **P2.3 Deterministic read-back.** A renderer from `Strategy` to plain English plus a table, covering every schema field, with snapshot tests per template.
- **P2.4 Builder graph.** The LangGraph graph in §5.1, with the SQLite checkpointer, interrupts for clarify and read-back, the repair loop (max 3), refine-as-patch, builder edits flowing back, and SSE streaming of node events and tokens.
- **P2.5 Guardrails.** An import test proving `backend.agent` can't reach `backend.live` or any order path; agent tools are compute-only; the grounding check on explanations; pasted content treated as untrusted; per-conversation cost caps.
- **P2.6 Tests.** A deterministic fake LLM for graph tests (interrupt and resume across a restart, the repair loop, refine, the edit-back path); recorded-response fixtures for the real provider; a parity test that a backtest run through the agent tool equals the same run through the HTTP endpoint; a smoke set of 10 hand-picked descriptions that must compile without edits.

**Gate:** from the API alone, a description compiles, clarifies, reads back, waits for approval across an API restart, backtests and explains; the import guardrail test is green; the 10-description smoke set passes.

### Phase 3: Product UX (3 to 4 weeks, overlapping Phase 2) → M1

- **P3.1 Strategy Studio.** Chat on the left; on the right, the read-back card (approve, or edit in the visual builder) and the run report. Assumptions are shown as editable chips. Version history and diff between versions. A **history sidebar** of past conversations (search, rename, delete, export) per §4.4; opening one shows its chat, strategy versions and results, and lets the trader continue refining.
- **P3.2 Data experience.** The data plan shown before a run; download progress toasts; a *Quit* button with the Keep/Discard dialog and *Remember my preference* checkbox; the startup prompt after an unclean exit; a status-bar session-cache size; a Data Manager page (library size per instrument, delete, size cap, retention preference, idle timeout).
- **P3.3 Reports.** The existing chart, performance and trade-log views wired to run history; the grounded explanation; comparing two versions side by side.
- **P3.4 Apply.** A one-click "Start paper" from an approved version, with the paper dashboard and Telegram alert setup reachable from the same screen. "Go live" exists only as a disabled control explaining that it arrives after Phase 7.
- **P3.5 Onboarding.** A first-run wizard: data folder, retention preference (defaulting to *Ask every time*), LLM key (or skip and use the builder), and optional Upstox connection with the morning-login explainer. A **no-broker path** with simulated data or CSV import, so someone can try the whole loop in five minutes.
- **P3.6 Frontend engineering.** A router, TanStack Query for server state, the generated API client, Vitest for components, one Playwright happy path (describe, approve, backtest, start paper on replay data), and basic accessibility (keyboard navigation, contrast). Keep the "synthetic data" badge everywhere simulated data appears.

**Gate (M1):** on a clean machine, from install to a running paper replay: type a strategy, answer at most two questions, approve the read-back, see a backtest with no manual download, start paper, quit and see the retention choice honoured, relaunch and reopen the conversation from history. Restarting mid-conversation resumes at the same pause. Every earlier gate is still green.

### Phase 4: Measure and harden → M2 (4 to 6 weeks)

- **P4.1 Eval set and harness.** 50 to 100 plain-English strategies with hand-written correct specs, including ambiguous, Hinglish and jargon-heavy cases, split dev/holdout about 70/30. Scores per field (entry, exit, legs, risk), valid-spec rate, questions asked, repair loops, cost and latency per compile, per model. CI runs a small subset against recorded responses; the full run is manual or nightly. The model choice for each graph step is decided here.
- **P4.2 Schema v2.** Expression-valued thresholds (percentile ranks, VIX- or IV-scaled values), regime-conditional parameters, range parameters for sweeps, risk-based sizing. A v1-to-v2 migrator; v1 documents stay loadable. Streaming and vectorized evaluation must still agree to 1e-9. Needs an India VIX series. The IR gains matching fields.
- **P4.3 Real option premiums.** If the P0.10 spike says Upstox Plus is viable: ingest strike-wise 1-minute candles for expired NIFTY and BANKNIFTY contracts and add a market-price provider to `OptionBook` with Black-Scholes as fallback. Either way: label each leg's premium source (market or model), report the share of fills priced from market data, and publish the model-vs-market error where both exist.
- **P4.4 Packaging.** The built UI served by FastAPI; a `trade-terminal` console entry point; install via `uv tool` or `pipx`; a version check at startup. A lightweight desktop wrapper (for example Tauri) that starts the server and opens the UI in its own window, so closing the window is unambiguously "quitting the app" and shows the Keep/Discard dialog natively (§4.1).
- **P4.5 Security.** Broker secrets and tokens move to the OS keychain (`.env` as an explicit fallback); a written threat model; a log-redaction test; CORS/Origin tests; dependency audits in CI; file-permission checks.
- **P4.6 Operations.** `trade-terminal doctor` (token status, instrument-master age, coverage, disk, versions, LLM key validity); a redacted diagnostics bundle; daily backup of the app DB and journals (market data excluded, as it's regenerable); migrations run and verified at startup.
- **P4.7 Compliance and copy.** Disclaimers (not investment advice, simulated vs real data, model vs market premiums); the LLM privacy notice; whatever the P0.10 terms and SEBI research require.
- **P4.8 Private beta.** 3 to 5 traders. Ask them what "constraints should not be point to point" meant and what "screener" meant; their answers gate Phase 5 and the wording of P4.2.

**Gate (M2):** an eval report with holdout numbers per model; option-premium coverage reported (or a recorded decision to ship labelled model premiums); someone else installs it on a second machine in under 15 minutes; 3 beta traders each run at least 5 strategies with no data loss; a crash-and-restart drill passes; the security checklist is complete.

### Phase 5: Screener and MCP (3 to 5 weeks)

Don't start until a beta trader has confirmed what "screener" means.

- **P5.1 Multi-instrument evaluation** of the condition language across a universe, daily bars first. Modes: scan now, scan history with forward returns, scan to a strategy's universe, scan to alerts.
- **P5.2 Survivorship and adjustments:** historical index membership, or labelled results; verify whether Upstox daily candles are split- and bonus-adjusted.
- **P5.3 Resumable prefetch jobs** with ETA under rate limits (200 stocks of intraday data is over two hours).
- **P5.4 Screener graph:** English to scan spec, read-back, run, results; approval before a scan feeds a strategy universe.
- **P5.5 Local MCP server (stdio):** validate strategy, run backtest (returns a job ID), job status, get report, list strategies, run scan. No order tools. Tested with at least two client models.

### Phase 6: Research agent and portfolio strategies (5 to 7 weeks) → M3

- **P6.1 Portfolio engine** on daily bars (universe, rank, rebalance, regime filter) behind the same seam, with a paper parity test.
- **P6.2 Advanced validation:** walk-forward, parameter-neighbourhood sweeps, slippage stress, a second-instrument rerun, deflated Sharpe from the P1.5 trial counts, and a final holdout the engine lets a strategy family touch once.
- **P6.3 Research graph:** `Send` fans out structural variants (a variant that only changes a number is rejected); a judge ranks by robustness; approval pauses with estimated cost before running; a research memory of what failed where.
- **P6.4 Throughput:** process-pool backtests with fixed seeds, results written to SQLite.

**Gate:** on pure-noise simulated data, the research graph reports zero survivors above the agreed threshold after deflation.

### Phase 7: Live trading (6+ weeks, gated) → M4

**Entry gates, both required:** the regulatory check is complete (tool vs provider status, Algo-ID handling, static IP), and you give explicit go-live sign-off. No real-order code merges before both.

- **P7.1 `UpstoxBroker`:** place, modify, cancel; order updates over the portfolio stream; partial fills and rejects; freeze-quantity slicing; idempotency through client tags; reconciliation at start and after every reconnect, refusing to trade on a mismatch.
- **P7.2 Mark-to-market kill switch:** account limits count unrealized loss (finding 10), plus max order size and notional, a fat-finger price band, an order-rate cap under 10 per second, and a server-side flatten-all.
- **P7.3 Independent watchdog** process that can flatten and cancel if the trading process dies or goes silent.
- **P7.4 WebSocket feed** wired in (the V3 decoder exists) for in-bar stops, with stale-feed detection.
- **P7.5 Progression:** paper, then shadow-live (orders generated, not sent), then 1 lot of 1 strategy for 2 weeks, then scale. At least 20 paper sessions with drift from backtest under an agreed threshold first.
- **P7.6 Deployment profile:** static IP (Mumbai VPS or home static IP); remote deployment makes API auth and TLS mandatory.
- **P7.7 Daily token handling:** morning reminder, one-click login, fail closed when no valid token exists at the open.
- **P7.8 "Apply → Live" UX:** typed confirmation, risk limits shown before confirming, an immutable order audit trail, compliance copy.
- **P7.9 Failure drills:** `kill -9`, a 60-second network cut, broker 5xx, duplicate-tag resend, clock skew, special sessions, expiry day.

**Gate:** all drills pass; daily reconciliation runs clean; 20 shadow sessions agree at order level; then the 2-week one-lot run.

### Phase 8: Hosted version (after the local app; to be scoped)

Outline only; it gets a detailed plan once M2 is reached and the local app has real users.

- Accounts and login, per-user data isolation (the `user_id` columns from Phase 1), Postgres and object storage behind the Phase 1 interfaces.
- Subscriptions and billing, with plans priced on live-strategy capacity.
- Server-side execution: a scheduler and workers per live strategy, per-user broker connections and daily token handling, orders routed through a registered static IP.
- Operations: monitoring, alerting, backups, incident runbooks, uptime targets.
- **Regulatory gate before any hosted live trading:** algo-provider empanelment with the exchanges and broker integration under SEBI's retail algo framework, confirmed by a lawyer. Keep AI market calls and trade signals out of the product, so it stays on the software side of the advice line.

## 9. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Compile accuracy is lower than it feels in demos | Core promise fails | Eval set with holdout (P4.1); deterministic read-back so errors are visible before anything runs |
| Upstox terms restrict local storage | Keep mode can't ship as designed | Spike in P0.10; Discard mode works regardless |
| Rate limits make first runs slow | Poor first impression | Base-timeframe-only downloads, data plan with ETA, Keep mode for heavy users |
| LLM cost per user | Users churn on cost | Bring-your-own key, caching, caps, eval-driven routing to cheaper models |
| Regulatory status of a distributed tool | Blocks beta or live | Research before beta copy (P0.10) and before any order code (Phase 7 gate) |
| Phase 2 and 3 overrun | M1 slips | Overlap is planned; cut OpenAI/Gemini/Ollama from M1; defer version diffing if needed |
| Dependency drift (pandas 3, numpy 2.5, duckdb 2) | Silent behaviour changes | Lockfile and CI in P0.5; upgrade deliberately |
| Solo developer, single commit history | Lost work, no review trail | Feature branches and CI from P0; push daily |

## 11. What changed from the 2026-10-01 plan

- Phase 1 split into **Platform** (P1), **Agent** (P2) and **UX** (P3), because the old Phase 1 held all three in 4 to 6 weeks.
- **App-session data cache with a Keep/Discard choice at quit, and permanent conversation history,** designed in full (§4), replacing the old "retention modes later" item.
- **Compile IR** introduced, because the engine schema can't be used directly with structured outputs (finding 20).
- **Code-generated read-back** and the rule that **the agent can't apply strategies** made explicit.
- **One LLM provider at M1**; others only on eval evidence or user demand.
- **Trial counter** moved into P1.5, where the run-history table is created.
- **Upstox Plus, data-terms and SEBI checks** moved into Phase 0 as spikes, because they decide storage layout and the Keep mode.
- Phase 0 gained findings 15 to 21: install fix, hermetic tests, vite upgrade, dependency pinning, schema param validation, tracked build cache.
- **No-broker onboarding** (simulated or CSV data) added, so new users can try the product immediately.

This plan is engineering guidance, not investment or legal advice.
